# Kettle Simulator — delivery plan

**Updated:** 2026-11-03  
**Status:** Approved

Подтверждённых календарных сроков нет. Оценки ниже отражают размер и риск работы, а не обещанные даты.

## Baseline

- Базовая симуляция поддерживает взятие, наполнение, нагрев, кипение, выкипание и сгорание чайника.
- Работают перелив, открытый кран без чайника, лужи и затопление комнаты.
- PR #2 синхронизирован с `main`, CI проходит, ручная проверка пользователем пройдена; требуется отдельное явное разрешение на merge.
- PR #4 с ролями project manager и visual designer слит в `main`.
- Следующая предлагаемая фича — свисток чайника; её Revision 1 находится `In review`.
- Подтверждённых target dates нет.

## Delivery order

1. Закрыть M0: получить разрешение и слить PR #2.
2. Обновить status/changelog после merge.
3. Провести ревью и явно утвердить спецификацию свистка.
4. Реализовать F1 отдельным PR: asset → development → QA → review → manual acceptance.
5. Отдельно описать и утвердить F2.
6. Реализовать SessionController, цель, результат и reset.
7. Провести 3–5 внешних playtests первого playable.
8. По результатам уточнить F3 и последующий roadmap.

## Definition of Ready

Фича допускается в разработку, если:

- есть proposal и номер revision;
- пользователь явно присвоил этой revision статус `Approved`;
- описаны цель, ценность, scope, out of scope и acceptance criteria;
- закрыты продуктовые решения;
- известны зависимости, ассеты и лицензии;
- указаны размер, риски и ручной playtest;
- owner и delivery item добавлены в `PROJECT_STATUS.md`.

## Definition of Done

Фича завершена, если:

- approved scope реализован без скрытого расширения;
- `bash scripts/check_project.sh` и CI проходят;
- QA и reviewer не имеют blocking findings;
- лицензии обновлены вместе с ассетами;
- ручной playtest пройден;
- пользователь принял заметное визуальное/игровое поведение;
- PR слит только после отдельного разрешения пользователя;
- proposal, `PROJECT_STATUS.md` и `CHANGELOG.md` актуализированы;
- известные ограничения записаны.

## Risk register

| Риск | Вероятность | Влияние | Митигация | Trigger |
|---|---|---|---|---|
| Scope creep | Высокая | Высокое | Одна механика на PR, строгий out of scope | Появляются несвязанные системы |
| Визуальные дефекты не видны CI | Высокая | Среднее | Обязательный manual visual gate | Есть только статический PASS |

| Дубли материалов/ассетов | Средняя | Среднее | Reuse-first и review paths | Создан аналог существующего ресурса |
| Некорректная лицензия | Низкая/средняя | Высокое | CC0-first и `LICENSES.md` | Нет URL/автора/лицензии |
| Наливание неудобно | Высокая | Высокое | Assisted controls и spike | Игрок не попадает в кружку |

## Release gates

### First playable

- полный сценарий от цели до результата;
- кипение понятно без debug HUD;
- есть успех, провал и restart;
- нет blocker/high дефектов;
- вода, нагрев и reset прошли regression;
- проведены 3–5 внешних playtests.

### Steam demo candidate

- Windows export запускается на чистой машине;
- есть главное меню, пауза, restart и выход;
- регулируются общая громкость и эффекты;
- input/resolution стабильны;
- save не ломает запуск;
- лицензии и attribution проверены;
- debug UI и ошибки Godot отсутствуют;
- производительность стабильна на целевой конфигурации;
- версия, changelog и store checklist актуальны.

## Approval flow

1. Product готовит proposal.
2. Пользователь ревьюит и явно утверждает конкретную revision.
3. Project создаёт delivery item.
4. Designer предлагает ассеты только для approved scope.
5. Developer реализует сфокусированный PR.
6. QA и reviewer независимо проверяют результат.
7. Пользователь выполняет ручную приёмку.
8. Только пользователь разрешает merge.
